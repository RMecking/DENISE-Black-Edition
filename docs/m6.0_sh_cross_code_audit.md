# M6.0 Black Edition / DENISE-SH cross-code audit

## A. Scope and interpretation

M6.0 is a source, architecture, and scientific-genealogy audit. It compares
DENISE Black Edition with the historical DENISE-SH repository without changing
either production tree. DENISE-SH is **not an oracle**: a function that exists
there is not thereby correct, reachable, complete, or verified. Textual
similarity is used only as genealogy evidence.

The audit distinguishes five states:

- **IMPLEMENTATION EXISTS**: source is present, regardless of reachability;
- **IMPLEMENTATION WIRED**: the normal production path can call it;
- **IMPLEMENTATION VERIFIED**: repository tests substantiate the claimed
  numerical behavior;
- **IMPLEMENTATION INCOMPLETE**: relevant pieces exist, but an end-to-end path
  or required mathematics is missing;
- **IMPLEMENTATION ABSENT**: no implementation of the capability was found.

Evidence is also typed explicitly as source text, build reachability, call-site
reachability, Git history, or runtime test. No runtime comparison was used to
infer correctness.

The DENISE-SH snapshot is dated 2020-08-09. Its README describes it as an SH
code with features similar to DENISE Black Edition. The file paths and Git blob

`tests/m6.0_sh_cross_code_inventory.json`.

One direction of transfer is explicit rather than inferred: DENISE-SH commit
`ae805416f31b66c67d2d075e49ea1e73b6178ff1` (2016-11-03) is titled
"Added PCG, LBFGS and Gauss-Filter modules from DENISE Black-Edition". Thus the
optimizer-module transfer was Black Edition to DENISE-SH. For most forward
kernels the audit establishes common ancestry, not a direction of copying.

## C. Build and runtime comparison

The unmodified DENISE-SH build was attempted in Ubuntu 22.04 WSL with GCC
11.4.0, Open MPI 4.1.2, and GNU Make 4.3:

```bash
make -C libcseife
make -C src denise
```

`libcseife` built with `mpicc`. The DENISE-SH executable did not: its Makefile
invokes the unavailable Intel `mpiicc` and contains historical cluster-specific
FFTW include/library paths. The result is therefore:

> **DENISE-SH BUILD NOT REPRODUCED**

No Makefile or source was edited to force a build. Because both unmodified
snapshots were not available as equivalent executables in the same environment,
M6.0 did not perform a forward-output comparison. This is an explicit coverage
limit, not a silent omission.

## F. SH free-surface audit

### Black Edition

`src/SH/sh.c` and `src/SH/sh_visc.c` contain commented blocks that refer to PSV
surface routines and PSV data structures. They are neither active nor valid SH
implementations that can simply be uncommented. In the active SH velocity and
stress kernels, `FREE_SURF` only suppresses the upper CPML contribution. No SH
routine imposes the traction condition by zeroing or mirroring the appropriate
staggered shear stress.

This confirms the already documented M5.6 coverage gap; it is not a newly
introduced solver regression.

### DENISE-SH

`surface_elastic_PML.c`, `surface_elastic_2nd.c`, and `surface_PML.c` exist and
are listed by the Makefile. In the normal `denise.c` and line-search paths,
however, calls to the PML surface routines are commented out. Git blame places
the commented main calls in the repository's first recorded commit, rather
than showing a later accidental disconnection. `surface_elastic_2nd.c` is
actively called only by a separate historical `denise_es.c` target and
hard-codes four ghost rows.

The elastic PML routine zeros and mirrors the normal SH shear traction for
`FDORDER/2` rows, but leaves part of the tangential-stress treatment commented.
The viscoelastic routine manipulates stress and some surface memory state, but
does not establish a fully audited ghost-row update for all GSLS memory
variables; several CPML arguments are unused. Since neither routine is active
in the normal SH path, neither is runtime evidence.

Conclusion: DENISE-SH offers useful historical equations and state-layout
clues, but not a complete implementation source that should be ported. An SH
free-surface implementation must be independently derived for the current
staggered grid and verified for reflection polarity, amplitude, phase,
stability, FD order, CPML interaction, and MPI seams.

## G. Viscoelastic forward comparison

The two codes share the same broad GSLS structure: relaxation-coefficient
preparation, trapezoidal memory-variable integration, FD orders 2 through 12,
halo exchange, and CPML placement are highly similar. DENISE-SH reads Qs using
the historical `taus=2/Qs` convention. That mapping is not a physical-Q
parameterization for multiple relaxation mechanisms and must not be ported.

Black Edition's current physical-Q input and L>1 rheology were repaired and
quantitatively verified in M4.2/M4.2.1. Those results supersede the historical
DENISE-SH parameterization. DENISE-SH has no equivalent verification artifact.

## H. Viscoelastic SH FWI comparison

DENISE-SH contains no attenuation gradient field, attenuation optimizer-vector
class, Q/tau chain rule, attenuation bounds, or attenuation model update. Its
PCG and LBFGS vectors have two material classes: Vs and density.

Black Edition contains more attenuation-related infrastructure, but source
reachability does not form an operational inversion:

- `waveconv_ts` and related fields are allocated, yet the normal viscoelastic
  gradient path does not accumulate a production shot attenuation gradient;
- the viscoelastic PCG store/extract helpers accept attenuation arguments but
  do not store or extract them;
- LBFGS has a third attenuation slot, but the material-change routine updates,
  bounds, and writes only Vs and density;
- `ptaus_old` is allocated without a complete reviewed update/reuse chain;
- no verified physical-Q to internal-tau gradient chain rule exists.

This corroborates the existing documentation: attenuation/Q inversion is a
deferred, unverified legacy capability. DENISE-SH does not contain missing
end-to-end pieces that could complete it.

## I. Elastic SH FWI comparison

The current Black Edition M5.1 path is the verified reference for this
repository. It applies the discrete-adjoint receiver metric, B-state density
correlation, PRE-stress material correlation, exact staggered X/Y material
transpose, physical Vs/density chain rule, MPI halo handling, and
`DT*DTINV` quadrature. M5.2 closes that implementation with formal Taylor tests.

The historical DENISE-SH path retains the legacy features isolated before the
M5.1 repair:

- residual receiver injection lacks the required inverse-density metric;
- stress correlation uses the legacy temporal state and same-cell material
  mapping rather than the exact staggered transpose;
- density correlation uses the legacy velocity state rather than the verified
  B state;
- no four-cell harmonic-mu material VJP is assembled;
- the time-domain gradient accumulation lacks the verified DTINV quadrature
  factor.

Its local conversion `2*rho*Vs*g_mu` is algebraically the correct Vs chain
factor; the defect is the legacy material gradient to which it is applied. Its
density expression is likewise structurally familiar but inherits the wrong
state and material transpose. DENISE-SH therefore confirms historical
genealogy, not the correctness of the old path.

## J. Optimizer and end-to-end model-update audit

Both repositories have reachable Vs/density PCG, LBFGS, descent, line-search,
bound, and model-write logic. The explicit 2016 DENISE-SH history records that
the optimizer modules came from Black Edition. Current Black Edition has the
newer modular driver and independently verified elastic gradients, but M6.0
does not claim optimizer convergence verification for either repository.

No complete attenuation update exists in DENISE-SH. Black Edition's partial
attenuation vector/storage infrastructure is disconnected from a complete
gradient, chain rule, bounded model update, and output/reuse loop.

## K. Answers to the nine audit questions

1. **Active DENISE-SH implementation missing in Black Edition?** No genuinely
   active normal SH feature was found. The visible free-surface files are not
   active in the normal DENISE-SH driver.
2. **Viscoelastic free-surface routine?** A routine exists, but its normal call
   sites are commented out.
3. **Complete enough to port?** No. It is historical reference material only.
4. **Complete attenuation gradient in DENISE-SH?** No.
5. **Attenuation optimizer-vector handling?** No; vectors cover Vs and density.
6. **Attenuation model update / Q-to-tau chain?** No.
7. **Historical `tau=2/Q` mapping?** Yes.
8. **Legacy elastic gradient defects?** Receiver metric, temporal state,
   staggered material VJP, density state, and DTINV scaling remain legacy. The
   local Vs chain factor itself is algebraically consistent.
9. **Black regression caused by incomplete DENISE-SH migration?** No evidence
   was found. Shared ancestry explains similarity, while free surface is
   disconnected in DENISE-SH from its first recorded state and attenuation
   inversion is absent there.

## L. Porting recommendations

### A. Strong candidate for independent implementation

- Elastic SH free surface, derived for the current staggered grid and tested
  independently. Extend to viscoelastic state only after the elastic boundary
  is closed.

### B. Historical reference only

- DENISE-SH surface equations and variable placement;
- legacy FWI loop ordering and optimizer ancestry.

### C. Superseded by verified Black Edition logic

- physical-Q parameterization and L>1 GSLS mapping;
- exact elastic Vs/density gradient and DTINV scaling;
- formal Taylor verification.

### D. Do not port

- `taus=2/Qs` for L>1 physical-Q input;
- legacy residual injection and same-cell/post-stress gradient correlations;
- missing four-cell harmonic-mu transpose and missing DTINV factor.

### E. Requires independent mathematical audit

- viscoelastic free-surface memory-variable treatment;
- attenuation parameterization, adjoint gradient, physical-Q chain rule,
  optimizer vector, bounds, update, and output/reuse semantics.

## M. Next milestone and verdict

The recommended M6.1 scope is an independently derived **elastic SH
free-surface verification and repair**, not a code port. It should establish an
analytical/semianalytical reflection oracle, polarity and phase checks,
multiple FD orders, CPML separation, and 1x1/2x1/1x2 MPI seam coverage. A
viscoelastic free-surface extension should follow only after the elastic case.
Attenuation inversion is larger and should remain a separate future milestone.
